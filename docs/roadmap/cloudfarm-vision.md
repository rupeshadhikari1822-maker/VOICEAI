# **CloudFARM Voice Studio**

## **Multilingual Nepali Speech Data Collection, ML Training & Voice AI Platform**

**Project:** CloudFARM / Himalaya Voice Engine  
**Repository:** voice-cloudfrm  
**Primary deployment:** DigitalOcean  
**Frontend:** Next.js / React  
**Backend:** Python / FastAPI  
**Database:** PostgreSQL  
**Object Storage:** S3-compatible storage  
**Processing:** Python + FFmpeg + VAD + ASR  
**ML:** Whisper/ASR, TTS, speaker/language/dialect models  
**AI Infrastructure:** CloudFARM GPU infrastructure  
**Production AI:** Himalaya Voice Engine + RAG  
**Development:** VS Code + GitHub + Claude Code

# **1. Executive Objective**

Build an enterprise-grade **online Voice Recording Studio** that allows distributed participants across Nepal to receive a secure recording link, complete their demographic and consent information, read assigned sentences, and submit high-quality speech recordings.

The platform must automatically:

1.  Register the participant.
2.  Collect required metadata.
3.  Obtain explicit recording/data consent.
4.  Assign a controlled recording session.
5.  Display one sentence at a time.
6.  Record the participant's voice directly in the browser.
7.  Validate microphone and recording conditions.
8.  Upload the original audio securely.
9.  Generate a quality-controlled processing copy.
10. Run automated audio-quality checks.
11. Detect silence, clipping, excessive noise and unusable recordings.
12. Associate each utterance with its exact transcript/script.
13. Organize recordings by language, dialect, region and speaker metadata.
14. Create versioned ML datasets.
15. Prepare data for ASR/TTS/speech-model training.
16. Export datasets to CloudFARM GPU infrastructure.
17. Evaluate trained models.
18. Connect the resulting speech models to the Himalaya Voice Engine.
19. Connect the voice engine to the CloudFARM RAG system.

The ultimate objective is to build a **proprietary, high-quality multilingual Nepal speech corpus** that can support Nepali and Nepal's diverse language/dialect ecosystem.

# **10. Important Privacy Rule Regarding Caste**

The original concept includes caste.

This requires special handling.

**Do not make caste mandatory by default.**

If caste/community information is scientifically necessary for the speech study, it should be:

  - explicitly explained
  - optional where possible
  - collected only with appropriate consent
  - separated from unnecessary public identifiers
  - access-controlled
  - excluded from model training metadata unless genuinely necessary
  - protected as sensitive demographic information

The platform should distinguish:

Identity information
        ≠
Research metadata
        ≠
Training metadata

A participant's personal identity should not automatically become part of the ML training dataset.

# **14. Recording Instructions**

Before recording, show concise instructions:

### **Environment**

Record in:

  - quiet room
  - closed doors/windows where possible
  - minimal echo
  - no television
  - no fan directly facing microphone
  - no traffic noise
  - no conversation nearby

### **Microphone**

Prefer:

  - headset microphone
  - USB microphone
  - good-quality wired microphone

Phone microphone is acceptable for controlled collection when necessary.

### **Participant position**

Maintain approximately:

10–20 cm

between mouth and microphone, depending on microphone type.

Do not repeatedly change position.

# **15. Recording Behavior**

The participant should:

1.  Read the sentence silently.
2.  Press record.
3.  Wait approximately 0.5 seconds.
4.  Speak naturally.
5.  Stop.
6.  Review.
7.  Submit.

The system should automatically detect:

  - no voice
  - very short recording
  - excessive silence
  - clipping
  - excessive background noise
  - low signal level
  - multiple speakers where detectable
  - incomplete speech

# **21. Quality Metrics**

Calculate:

### **Duration**

Reject recordings that are too short.

### **Silence ratio**

Detect excessive silence before/after speech.

### **RMS / loudness**

Detect recordings that are too quiet or too loud.

### **Peak level**

Detect clipping.

### **Clipping ratio**

Detect distorted recordings.

### **SNR**

Estimate background-noise level.

### **Voice activity**

Determine whether speech is actually present.

### **Transcript consistency**

Compare expected sentence with ASR output.

# **22. Quality Score**

Create a standardized score:

Audio Quality Score
        │
        ├── Signal level
        ├── Noise
        ├── Clipping
        ├── Silence
        ├── Duration
        ├── Speech activity
        └── Transcript consistency

Example:

90–100  Excellent
75–89   Good
60–74   Review
\<60     Reject

These thresholds should be configurable rather than hard-coded.

# **23. Never Automatically Delete Raw Data**

If an utterance fails quality control:

status = rejected

rather than immediately deleting it.

Keep the original according to the project's retention policy.

This allows the research team to inspect false rejections and improve the quality model.

# **30. Data Leakage Prevention**

The same speaker must not appear randomly in:

validation
test

Instead:

Speaker-level split

Validation  10%

The exact percentages can change, but the fundamental rule is:

**Do not allow the same speaker's recordings to leak across evaluation sets.**

Otherwise model performance can appear artificially high.

# **48. Dataset Quality Principles**

The goal is not:

"Collect as many recordings as possible."

The goal is:

**Collect the most useful, diverse, accurately labeled and ethically obtained speech data possible.**

Prioritize:

  - speaker diversity
  - geographic diversity
  - language diversity
  - dialect diversity
  - age diversity
  - gender diversity where appropriate
  - acoustic diversity
  - pronunciation diversity
  - natural speech
  - accurate transcripts
  - consistent recording protocols

# **49. Avoid Over-Collecting One Speaker**

Maximum 500 utterances/speaker

The exact limits should be configurable.

This prevents the corpus from becoming dominated by a small number of voices.

# **71. Definition of Success**

The project is successful when a participant in Nepal can open a link on a mobile phone, select/confirm their language information, provide consent, record a sentence in a quiet environment, submit it reliably over a normal mobile network, and have the recording automatically stored, processed, quality-scored and associated with its verified transcript.

The research team must then be able to transform thousands or millions of such recordings into controlled, versioned and de-identified ML datasets.

Finally, those datasets must be capable of being transferred to CloudFARM GPU infrastructure for ASR/TTS experimentation and eventually integrated into the Himalaya Voice Engine.

The end product is therefore not merely an online recorder.

It is:

**CloudFARM Voice Studio → Nepal Speech Corpus → ML Training Infrastructure → Himalaya Voice Engine → RAG-Powered Multilingual Voice Bot.**
